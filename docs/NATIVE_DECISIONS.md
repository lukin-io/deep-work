# Native implementation decisions

Stage 1 decisions, October 18, 2026. The specification remains the product contract; these notes resolve native implementation choices and disclose temporary milestone limitations. Acceptance status stays exclusively in [IMPLEMENTATION_CHECKLIST.md](../IMPLEMENTATION_CHECKLIST.md), with results in [VERIFICATION.md](VERIFICATION.md).

## Platform and project

- Minimum deployment target: **macOS 13**. SwiftUI renders the content; AppKit owns the real window, application menus, status item, and tab keyboard handling. Persistence uses the system SQLite library through `SQLite3`; no third-party dependencies are introduced.
- `DeepWork.xcodeproj` contains the `DeepWork` application target and a hostless `DeepWorkCoreTests` target. Both link the local `DeepWorkCore` Swift package. The application module is `DeepWorkApp`, bundle identifier is `app.deepwork.mac`, bundle is `Deep Work.app`, and executable is `DeepWork`.
- The local package reference `.` is relative to the project directory containing `DeepWork.xcodeproj`; it points to the root `Package.swift`, not inside the `.xcodeproj` bundle. The project generator checks in explicit application/test source references; rerun it after adding or removing those sources.
- Full Xcode **16 or later** is required for the Swift Testing test sources. Swift language mode remains 5, with complete strict-concurrency checking in the Xcode project. The Command Line Tools build uses the same Swift package sources and produces an ad hoc signed local app. Distribution signing, notarization, sandboxing, and a release installer are outside this milestone.
- Full Xcode is absent on the implementation machine. Project syntax and references can be checked here; an actual Xcode project build remains unverified. See README for verified commands and the exact tooling limitation.

## State, navigation, and window lifecycle

- One retained application delegate constructs one `@MainActor AppModel`, one window controller, and one status item. Views observe that model; changing tabs does not reconstruct domain state or stores. No New Window command or independent window-owned timer exists.
- Journal is selected on each process launch. The last-selected tab is intentionally not persisted. Report selection, schedule drafts, export scope, and unsaved feedback remain in memory while changing tabs. The schedule editor itself is deferred to Stage 3.
- Native tab order is Focus, Journal, Settings. The segmented control handles Left/Right wrapping and Home/End only while it owns keyboard focus, leaving text-field editing keys alone.
- Use native title-bar controls. Close and Command-W save committed state and hide the retained window; the process remains alive. The status item and File → Show Deep Work select Focus and reopen the existing window. Dock reopen restores the existing selection. Minimize uses the Dock, Zoom uses AppKit, and native full-screen is enabled.
- Preferred content widths follow the reference: Focus 390 pt, Journal 696 pt, Settings 560 pt. Minimum content size is 320 × 420 pt. Content scrolls vertically; tab changes fit the preferred size to the available screen, without resizing a full-screen window.
- Window resizing receives selection updates on `RunLoop.main`. `@Published` emits before assigning the new value; resizing synchronously caused `NSHostingController` to lay out the preceding panel. Deferred resize allows the selected tab and visible panel to change together. The corresponding integration test and manual reproduction belong in the verification record.
- Native menus intentionally include Deep Work (About, Hide, Quit), File (Show Deep Work, Close Window), Edit (Undo, Cut, Copy, Paste, Select All), and Window (Minimize, Zoom, Toggle Full Screen). Control-Command-F toggles native full-screen. These replace the prototype's decorative menu labels.
- Explicit Quit writes committed model snapshots and exits. Unsaved feedback is not promoted to a saved draft by Quit or Close. No running timer exists yet, so close/pause/checkpoint integration is not claimed complete.

## Durable models and validation

- Codable value models separate setup configuration, finalized focus records, a sealed active checkpoint, work schedule, and settings. Session IDs are UUIDs. Original absolute timestamps and ordered active segments are retained; reports will derive totals rather than storing rounded display numbers.
- Focus selections start blank, custom values start at 75/15 minutes, and Repeat starts on. Valid duration edits and Repeat changes persist immediately. Invalid custom input remains an in-memory edit; it does not replace the last valid persisted number. Timer creation and boundary accounting remain Stage 2 work.
- Records validate identifiers, finite timestamps, timestamp/segment order, positive nonoverlapping segments within the session, duration bounds, unique journal IDs, and complete/partial/live restrictions. Complete records must contain their planned active duration, with a 1 ms serialization tolerance. Zero-time abandoned records and live observations cannot enter finalized history.
- Checkpoints store remaining seconds and sealed segments, with no live wall-clock deadline. This prepares paused recovery without crediting process downtime. Stage 2 must implement and verify recovery; merely decoding a checkpoint does not resume it or prove recovery behavior.
- Schedule defaults are Monday–Friday, Monday week start, and midnight cutoff. Rotating shifts retain a Gregorian civil date anchor, rather than a UTC instant. Zero chosen weekdays is valid; duplicate weekdays, invalid dates, shifts outside 1–31 days, and cutoffs outside 00:00–23:59 are rejected. Calendar allocation, DST rules, and schedule draft save/cancel are deferred.

## Storage and failure handling

- **SQLite is the canonical native store.** Resolve the user's Application Support directory through `FileManager`, then use the bundle-ID subdirectory: `~/Library/Application Support/app.deepwork.mac/DeepWork.sqlite` for this unsandboxed app. This follows Apple's placement and naming guidance for app-managed data. A future sandboxed build must keep using the system directory API and deliberately migrate existing data. [Apple: Application Support](https://developer.apple.com/documentation/foundation/url/applicationsupportdirectory), [Apple: macOS Library directories](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/FileSystemProgrammingGuide/MacOSXDirectories/MacOSXDirectories.html).
- Schema version 1 uses `PRAGMA user_version`. `session_records` has one row per actual focus record, keyed by UUID, with explicit ordering and a Codable payload. Singleton `journal_state` contains configuration, schedule, and the active checkpoint; singleton `settings` contains all settings and the explicitly saved feedback draft. Payload timestamps retain milliseconds since the Unix epoch. There is no ongoing JSON-file or UserDefaults persistence, and no example records enter the actual journal.
- A shared serial queue per canonical database path coordinates both logical stores. Short-lived connections enable foreign keys, WAL, `synchronous=FULL`, and a 250 ms busy timeout. Reads use a consistent transaction; writes use `BEGIN IMMEDIATE` with checked commit and rollback on failure. Full snapshot writes retain the existing lightweight Store APIs. SQLite still admits one writer at a time; a lock failure is reported rather than discarded. [SQLite transactions](https://www.sqlite.org/lang_transaction.html), [SQLite pragmas](https://www.sqlite.org/pragma.html).
- Newly created app directories use mode 0700 and databases 0600. Existing permissions are only restricted, never broadened; parent Application Support permissions are untouched. WAL and SHM sidecars stay beside the database. Committed changes can remain in WAL, so copying a live `DeepWork.sqlite` alone is not a complete backup; future backup functionality must use a consistent SQLite snapshot. [SQLite WAL](https://www.sqlite.org/wal.html).
- The app proves a committed write before showing a healthy saved status. Configuration changes, explicit draft saves, Close, and Quit use the durable operations. A missing database alone is not proof of write access, and a failed operation cannot replace existing data with defaults.
- Malformed payloads, unsupported schema versions, invalid models, and read/write failures latch a visible warning for the affected logical store. Journal payload corruption does not stop otherwise valid settings operations, or vice versa. Physical database failures, permissions, and unsupported database versions can affect both stores because they share one file. In-memory values and edits remain usable, and success is reported only after commit. No destructive repair or retry control is added.
- Database operations remain synchronous in Stage 1; each SQLite lock wait uses the 250 ms timeout. Before frequent timer checkpoints, move potentially lengthy encoding/file work off the main actor while retaining transaction order and accurate result publication. `FULL` is an explicit durability choice, not evidence that power-loss recovery has been tested.
- Debug builds accept `DEEP_WORK_DATA_DIR` for isolated tests and never inspect the user's real legacy directory when that override is set. Release builds use the system Application Support location.

## Migration from the initial JSON implementation

- When the canonical database is absent, load and validate `deep-work-journal-v1.json` and `deep-work-settings-v1.json` from the chosen data directory and, on normal launch, the earlier `~/Library/Application Support/Deep Work/` directory. Missing files use documented defaults; unreadable, malformed, or unsupported files cause a visible failure. Different copies of the same legacy filename cause a conflict rather than choosing one silently.
- Create the complete schema and migrated rows in one transaction inside an owned temporary SQLite file in the destination directory. Bootstrap uses the rollback journal; close the connection before publishing the database through a same-directory move that cannot overwrite an existing destination. Failure publishes no partial database and preserves both legacy source files.
- First-time migration is deliberately all-or-nothing: an invalid legacy settings file also prevents publication of migrated journal data. This differs from the independent logical error handling inside an already valid database. Correct the underlying file/permission problem and relaunch to retry; no existing history is discarded.
- Once the canonical database exists, it is authoritative. Retained legacy JSON files are never reimported over SQLite changes and are not kept in sync. This makes migration idempotent while preserving the original files. Browser localStorage is not imported automatically.

## Settings draft and interim presentation

- Save Draft is implemented now so settings persistence has an actual user workflow. Feedback edits remain separate from the saved draft; tab changes and unrelated configuration saves never save the unsaved form. Copy Feedback and feedback delivery are not implemented.
- Preserve JavaScript length semantics with UTF-16 code units. Use ECMAScript whitespace trimming, a trimmed minimum of 5 message units, a raw maximum of 5,000 message units, the 254-unit email limit, and HTML-compatible single-address shape validation. Email errors take priority. Unknown stored feedback types fall back to General feedback. Validation checks address shape, not deliverability.
- The launch Boolean records preference only. The disabled Launch at Login control makes no claim about actual OS registration; ServiceManagement state, approval, revocation, and real login verification remain Stage 5 work.
- The three views retain the reference's minimal structure and labels. Controls for unavailable timer, reporting, schedule, example, export, and clipboard functions are disabled and accompanied by concise availability text. Journal metrics show dashes instead of invented calculations; existing history is retained even though its report is not rendered yet.
- Fresh launch opens Journal without generated examples in this milestone. The reference's initial example experience is deferred to Stage 3, and AC-01 is therefore not fully accepted. No sample content is presented as real history.
- Native failure text replaces references to a browser or preview. The interim journal warning explicitly says CSV is unavailable, rather than instructing the user to use an unimplemented export. J-052 remains incomplete until native timing and export also work during storage failure.
- Slack remains an explicitly labelled preview of **❌ Deep WORK, DND**. No authentication or remote status change occurs. The native status item currently displays the idle Deep Work label; countdown and pause-icon behavior depend on later timer work.
