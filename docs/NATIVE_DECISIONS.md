# Native implementation decisions

Stage 1 and Stage 2 decisions, October 18, 2026. The specification remains the product contract; these notes resolve native implementation choices and disclose temporary milestone limitations. Acceptance status stays exclusively in [IMPLEMENTATION_CHECKLIST.md](../IMPLEMENTATION_CHECKLIST.md), with results in [VERIFICATION.md](VERIFICATION.md). Recording a decision here does not establish native verification.

## Platform and project

- Supported platform: **Apple Silicon (arm64), macOS 15 or later**. The October 18 user instruction excludes Intel and very old macOS; macOS 15 is the selected floor and native CI baseline. This supersedes the earlier macOS 13 choice. SwiftUI renders the content; AppKit owns the real window, application menus, status item, and tab keyboard handling. Persistence uses the system SQLite library through `SQLite3`; no third-party dependencies are introduced.
- `DeepWork.xcodeproj` contains the `DeepWork` application target and a hostless `DeepWorkCoreTests` target. Both link the local `DeepWorkCore` Swift package. The application module is `DeepWorkApp`, bundle identifier is `app.deepwork.mac`, bundle is `Deep Work.app`, and executable is `DeepWork`.
- The local package reference `.` is relative to the project directory containing `DeepWork.xcodeproj`; it points to the root `Package.swift`, not inside the `.xcodeproj` bundle. The project generator checks in explicit application/test source references; rerun it after adding or removing those sources.
- Full Xcode **16 or later** is required for the Swift Testing test sources. Swift language mode remains 5, with complete strict-concurrency checking in the Xcode project. The Command Line Tools build uses the same Swift package sources and produces an ad hoc signed local app. Developer ID signing, notarization and sandboxing remain outside this milestone; previews use the verified ZIP release path documented below.
- Full Xcode is absent on the implementation machine. The actual Release project and asset catalog build passed on hosted Xcode 16.4 with the macOS 15.5 SDK; local CLT compilation remains separate evidence. See README and VERIFICATION.md for commands and CI results.
- The user supplied approved Icon 1.0 exports. After the requested cleanup, `DeepWork/Resources/Assets.xcassets/AppIcon.appiconset` is the single production source; the standalone master was byte-identical to its largest image. Xcode compiles `AppIcon` through Resources. The CLT build packages the catalog's existing PNGs with Apple's `iconutil`, without resizing or recoloring, into `Contents/Resources/AppIcon.icns`, referenced by `CFBundleIconFile`. Native ImageIO/AppKit checks compare all ten standard/Retina representations with the catalog's pixels. Delivery originals are preserved in an ignored local archive outside build output, with hashes in [APP_ICON.md](APP_ICON.md); no build or test depends on that archive. The alternate Icon Composer interpretation remains unused. This flat icon route supports the macOS 15 deployment floor; Xcode 16.4 compiled the asset catalog successfully in hosted CI. [Apple: configuring an app icon](https://developer.apple.com/documentation/xcode/configuring-your-app-icon), [Apple: CFBundleIconFile](https://developer.apple.com/documentation/bundleresources/information-property-list/cfbundleiconfile), [Apple: app icons HIG](https://developer.apple.com/design/human-interface-guidelines/app-icons).
- Rebuilding the existing local app originally left its root directory timestamp unchanged; LaunchServices and the About panel continued showing the previously cached generic icon despite valid resources. The CLI packaging script now touches the app bundle after signing, matching Xcode's final bundle-touch behavior. Native reproduction confirmed that quitting, touching only that bundle, and reopening displayed the approved icon; `NSWorkspace.icon(forFile:)` also returned the blue artwork afterward. No application-level icon override or global cache reset is used.

## State, navigation, and window lifecycle

- One retained application delegate constructs one `@MainActor AppModel`, one window controller, and one status item. Views observe that model; changing tabs does not reconstruct domain state or stores. No New Window command or independent window-owned timer exists.
- Journal is selected on each process launch. The last-selected tab is intentionally not persisted. Report selection, schedule drafts, export scope, and unsaved feedback remain in memory while changing tabs. The schedule editor itself is deferred to Stage 3.
- Button focus requests follow the user’s macOS Keyboard navigation preference; no global preference is changed and no duplicate focus wrapper is introduced. Text editing still receives focus/select-all when Custom is selected. [Apple: focus in SwiftUI](https://developer.apple.com/videos/play/wwdc2023/10162/).
- Native tab order is Focus, Journal, Settings. The segmented control handles Left/Right wrapping and Home/End only while it owns keyboard focus, leaving text-field editing keys alone. Entering Focus through a tab preserves tab focus; an explicit status-item/File reopen request focuses the appropriate Focus control. This avoids a Focus appearance handler stealing the next navigation key. Tab changes reconcile and persist elapsed boundaries before displaying the selected panel.
- Use native title-bar controls. The user clarified that red close and Command-W only hide the retained main window. Running focus/break continues, paused state stays paused, and delayed boundaries still reconcile exactly once. An ordinary checkpoint is queued without waiting, freezing controls, creating a partial record or gating hide on storage success. Menu-bar click and File → Show Deep Work bring the existing window forward on Focus without restarting; Dock reopen restores the existing selection. Hide, Minimize and tab changes also preserve timing. Zoom uses AppKit, and native full-screen is enabled.
- Preferred content widths follow the reference: Focus 390 pt, Journal 696 pt, Settings 560 pt. Minimum content size is 320 × 420 pt. Content scrolls vertically; tab changes fit the preferred size to the available screen, without resizing a full-screen window.
- Window resizing receives selection updates on `RunLoop.main`. `@Published` emits before assigning the new value; resizing synchronously caused `NSHostingController` to lay out the preceding panel. Deferred resize allows the selected tab and visible panel to change together. The corresponding integration test and manual reproduction belong in the verification record.
- Native menus intentionally include Deep Work (About, Hide, Quit), File (Show Deep Work, Close Window), Edit (Undo, Cut, Copy, Paste, Select All), and Window (Minimize, Zoom, Toggle Full Screen). Control-Command-F toggles native full-screen. These replace the prototype's decorative menu labels.
- Only full Quit freezes timer/configuration controls while ordered persistence drains. Quit reconciles and pauses, saves committed settings/journal/checkpoint state, then exits. A failed Quit offers Keep Open by default and explicit Quit Without Saving; Keep Open restores controls and retains in-memory state. Relaunch restores unfinished work paused without counting process downtime. Explicit Save Draft semantics remain: unsaved feedback is retained by window hide/reopen but is not promoted to a saved draft by Close or Quit. Invalid duration edits do not replace validated stored values.
- AppKit routes red close and Command-W through `windowShouldClose`, which hides the retained window immediately and returns false to avoid destroying it. Quit uses `applicationShouldTerminate` and `terminateLater` to drain writes, because the window-close delegate is not called during Quit. The earlier asynchronous close/pause barrier was removed following the user’s correction. [Apple: windowShouldClose](https://developer.apple.com/documentation/appkit/nswindowdelegate/windowshouldclose(_:)), [Apple: applicationShouldTerminate](https://developer.apple.com/documentation/appkit/nsapplicationdelegate/applicationshouldterminate(_:)).

## Timer, accounting, and recovery

- The engine receives an injectable elapsed-time source and civil timestamp. Production uses Swift `ContinuousClock`: elapsed time includes sleep while the process remains alive. Windows hidden with red close, Command-W or Command-H, minimized windows, and delayed callbacks reconcile every crossed phase boundary in order, exactly once. The app does not prevent system sleep or infer user attention. This deliberately preserves elapsed, unpaused timer behavior; `SuspendingClock`, which stops during sleep, would define a different product policy. [Apple: ContinuousClock](https://developer.apple.com/documentation/swift/continuousclock), [Apple: SuspendingClock](https://developer.apple.com/documentation/swift/suspendingclock).
- A logical civil timeline starts from the wall-clock anchor and advances by monotonic elapsed time. Changing the system clock during an active session cannot add focus, reverse its segments, or alter the countdown. Start and Start again establish a new civil anchor; ordinary pause/resume and repeating phases retain the existing timeline. Recovery reanchors no earlier than the saved timestamp, and recovered Resume may advance that anchor to current civil time, preventing a backward clock adjustment from placing a resumed segment before saved work. This is an intentional correction to the prototype's wall-clock accounting limitation. Absolute dates and sealed segments are persisted; process-local clock instants are never persisted.
- Focus and break durations are snapshotted at Start. Each focus owns a stable record UUID; each phase owns a separate identity. Full active focus becomes Complete only at its exact deadline. Early Take break or End session retains positive focus as Partial; zero-time abandoned focus creates no finalized record. Pause seals the current segment, Resume opens another on the same record, and breaks never create focus segments.
- Reconcile before every timer action. Manual Take break, Skip break, and Finish break capture phase identity: if catch-up enters a different phase instance, the stale action only refreshes state. This explicitly tightens the prototype's phase-name guard, including delays crossing whole pairs and returning to another focus. Pause and End session intentionally act on the reconciled current state. Changing Repeat first reconciles with its previous value, then applies the new preference.
- Take break from paused focus and Skip break from paused break start the next phase running. Finish break from paused break completes the pair. Changing Repeat alone never resumes a paused timer or starts a completed pair; Start again is explicit.
- Persist a sealed snapshot approximately every five elapsed seconds while running and on actions, phase transitions, close, and sleep notification. Records and active checkpoint share a SQLite transaction. A clean Quit drains queued writes before termination. An abrupt crash restores the last committed point and may lose the uncommitted interval; downtime creates no focus. Recovered focus and break require explicit Resume and display the specified recovery notice. The normal launch tab remains Journal.
- Sleep notifications checkpoint current state; wake reconciliation uses the elapsed clock. Observers use `NSWorkspace.shared.notificationCenter`, as required by AppKit. Sleep does not become an implicit Pause. [Apple: willSleepNotification](https://developer.apple.com/documentation/appkit/nsworkspace/willsleepnotification).
- One retained `AppModel` owns the timer. A per-store process lock (`flock`) prevents a second process using the same data directory from obtaining timer/storage ownership. The native app denies that duplicate instance instead of recreating the browser's passive second-preview mode. The lock remains held for the owner's lifetime and releases on exit or crash; it is separate from SQLite's transaction lock. Another isolated Debug data directory may run independently.
- One application-owned refresh loop projects the engine into Focus and the retained status item; views do not own accounting or timers. Countdown formatting rounds remaining seconds upward, expands minutes through 480:00, and clamps completion to 00:00. Paused state freezes the projection. Native UI, lifecycle, sleep, and recovery acceptance must be recorded separately from deterministic engine tests. The user requested full native phase names: the menu bar uses `MM:SS - Deep work` / `MM:SS - Break`, replacing the prototype’s abbreviated lowercase labels; idle/completed still reads Deep Work.
- Native accessibility labels, error hints, phase announcements, and reduced-motion handling support Focus interaction. Programmatic accessibility inspection and keyboard tests do not establish a complete VoiceOver acceptance pass; that remains separately unverified until exercised with VoiceOver.

## Durable models and validation

- Codable value models separate setup configuration, finalized focus records, a sealed active checkpoint, work schedule, and settings. Session IDs are UUIDs. Original absolute timestamps and ordered active segments are retained; reports will derive totals rather than storing rounded display numbers.
- Focus selections start blank, custom values start at 75/15 minutes, and Repeat starts on. Valid duration edits and Repeat changes queue persistence immediately. Invalid custom input remains an in-memory edit; it does not replace the last valid persisted number. Start revalidates both choices and snapshots the selected durations.
- Records validate identifiers, finite timestamps, timestamp/segment order, positive nonoverlapping segments within the session, duration bounds, unique journal IDs, and complete/partial/live restrictions. Complete records must contain their planned active duration, with a 1 ms serialization tolerance. Zero-time abandoned records and live observations cannot enter finalized history.
- Checkpoints store remaining seconds and sealed segments, with no live wall-clock deadline. Recovery restores the same live focus record and remainder paused, or a paused break without a focus record. Validation rejects invalid durations, inconsistent focused time/remainder, and a checkpoint record duplicated in finalized history. The existing version 1 schema already supports this contract; Stage 2 requires no database migration.
- Schedule defaults are Monday–Friday, Monday week start, and midnight cutoff. Rotating shifts retain a Gregorian civil date anchor, rather than a UTC instant. Zero chosen weekdays is valid; duplicate weekdays, invalid dates, shifts outside 1–31 days, and cutoffs outside 00:00–23:59 are rejected. Calendar allocation, DST rules, and schedule draft save/cancel are deferred.

## Storage and failure handling

- **SQLite is the canonical native store.** Resolve the user's Application Support directory through `FileManager`, then use the bundle-ID subdirectory: `~/Library/Application Support/app.deepwork.mac/DeepWork.sqlite` for this unsandboxed app. This follows Apple's placement and naming guidance for app-managed data. A future sandboxed build must keep using the system directory API and deliberately migrate existing data. [Apple: Application Support](https://developer.apple.com/documentation/foundation/url/applicationsupportdirectory), [Apple: macOS Library directories](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/FileSystemProgrammingGuide/MacOSXDirectories/MacOSXDirectories.html).
- Schema version 1 uses `PRAGMA user_version`. `session_records` has one row per actual focus record, keyed by UUID, with explicit ordering and a Codable payload. Singleton `journal_state` contains configuration, schedule, and the active checkpoint; singleton `settings` contains all settings and the explicitly saved feedback draft. Payload timestamps retain milliseconds since the Unix epoch. There is no ongoing JSON-file or UserDefaults persistence, and no example records enter the actual journal.
- A shared serial queue per canonical database path coordinates both logical stores. Short-lived connections enable foreign keys, WAL, `synchronous=FULL`, and a 250 ms busy timeout. Reads use a consistent transaction; writes use `BEGIN IMMEDIATE` with checked commit and rollback on failure. Full snapshot writes retain the existing lightweight Store APIs. SQLite still admits one writer at a time; a lock failure is reported rather than discarded. [SQLite transactions](https://www.sqlite.org/lang_transaction.html), [SQLite pragmas](https://www.sqlite.org/pragma.html).
- Newly created app directories use mode 0700 and databases 0600. Existing permissions are only restricted, never broadened; parent Application Support permissions are untouched. WAL and SHM sidecars stay beside the database. Committed changes can remain in WAL, so copying a live `DeepWork.sqlite` alone is not a complete backup; future backup functionality must use a consistent SQLite snapshot. [SQLite WAL](https://www.sqlite.org/wal.html).
- The app proves a committed write before showing a healthy saved status. Configuration changes, explicit draft saves, Close, and Quit use the durable operations. A missing database alone is not proof of write access, and a failed operation cannot replace existing data with defaults.
- Malformed payloads, unsupported schema versions, invalid models, and read/write failures latch a visible warning for the affected logical store. Journal payload corruption does not stop otherwise valid settings operations, or vice versa. Physical database failures, permissions, and unsupported database versions can affect both stores because they share one file. In-memory values and edits remain usable, and success is reported only after commit. No destructive repair or retry control is added.
- During timer operation, ordered persistence moves encoding/file work off the main actor and publishes results back to the shared model. Pending writes do not establish successful saving; failure remains visible while in-memory timing continues. Each SQLite lock wait retains the 250 ms timeout. `FULL` is an explicit durability choice, not evidence that power-loss recovery has been tested.
- Debug builds accept `DEEP_WORK_DATA_DIR` for isolated tests and never inspect the user's real legacy directory when that override is set. Release builds use the system Application Support location.

## Migration from the initial JSON implementation

- When the canonical database is absent, load and validate `deep-work-journal-v1.json` and `deep-work-settings-v1.json` from the chosen data directory and, on normal launch, the earlier `~/Library/Application Support/Deep Work/` directory. Missing files use documented defaults; unreadable, malformed, or unsupported files cause a visible failure. Different copies of the same legacy filename cause a conflict rather than choosing one silently.
- Create the complete schema and migrated rows in one transaction inside an owned temporary SQLite file in the destination directory. Bootstrap uses the rollback journal; close the connection before publishing the database through a same-directory move that cannot overwrite an existing destination. Failure publishes no partial database and preserves both legacy source files.
- First-time migration is deliberately all-or-nothing: an invalid legacy settings file also prevents publication of migrated journal data. This differs from the independent logical error handling inside an already valid database. Correct the underlying file/permission problem and relaunch to retry; no existing history is discarded.
- Once the canonical database exists, it is authoritative. Retained legacy JSON files are never reimported over SQLite changes and are not kept in sync. This makes migration idempotent while preserving the original files. Browser localStorage is not imported automatically.

## Settings draft and interim presentation

- Save Draft is implemented now so settings persistence has an actual user workflow. Feedback edits remain separate from the saved draft; tab changes and unrelated configuration saves never save the unsaved form. Copy Feedback and feedback delivery are not implemented.
- Preserve JavaScript length semantics with UTF-16 code units. Use ECMAScript whitespace trimming, a trimmed minimum of 5 message units, a raw maximum of 5,000 message units, the 254-unit email limit, and HTML-compatible single-address shape validation. Email errors take priority. Unknown stored feedback types fall back to General feedback. Validation checks address shape, not deliverability.
- The launch Boolean records preference only. The disabled Launch at Login control makes no claim about actual OS registration; ServiceManagement state, approval, revocation, and real login verification remain Stage 5 work.
- The three views retain the reference's minimal structure and labels. Stage 2 enables the Focus setup, timer controls, and recovery notice. Controls for unavailable reporting, schedule, example, export, and clipboard functions remain disabled and accompanied by concise availability text. Journal metrics show dashes instead of invented calculations; recorded history is retained even though its report is not rendered yet.
- Fresh launch opens Journal without generated examples in this milestone. The reference's initial example experience is deferred to Stage 3, and AC-01 is therefore not fully accepted. No sample content is presented as real history.
- Native failure text replaces references to a browser or preview. The interim journal warning explicitly says CSV is unavailable, rather than instructing the user to use an unimplemented export. J-052 remains incomplete until export also works during storage failure. Saved-success captions must reflect committed persistence; pending or failed writes cannot imply a durable journal save.
- Slack remains an explicitly labelled preview of **❌ Deep WORK, DND**. No authentication or remote status change occurs. Status-item countdown, phase text, paused icon, and Focus reopen use the same timer state; native acceptance remains documented independently from implementation.

## GitHub distribution

- User-requested app downloads belong in `lukin-io/deep-work` GitHub Releases. A release contains an optimized Apple Silicon app ZIP, checksums and source/build metadata; temporary CI artifacts and automatic source archives do not satisfy app delivery. Versioned release notes disclose product and platform limits.
- Preview tags explicitly identify the early state: `vX.Y.Z-preview.N`. The numeric version matches the app bundle, and the annotated tag binds a clean source commit. Published tags/assets are not replaced. The first requested preview can be built from the open app PR; later normal releases use reviewed `main`.
- Build arm64 with Swift Release configuration and the macOS 15 deployment triple, add the canonical icon and license, sign, and package using Apple's `ditto` ZIP guidance. Verify the extracted app and archive manifest; copy no settings, SQLite files, development fixtures or local icon originals. [Apple: packaging Mac software](https://developer.apple.com/documentation/xcode/packaging-mac-software-for-distribution).
- There are no valid code-signing identities on this machine. The initial channel is therefore an explicitly ad hoc signed, unnotarized prerelease, never Latest. Stable tags are rejected. A future stable channel requires Developer ID, hardened runtime, timestamping, notarization, stapling and Gatekeeper checks; publishing a ZIP is not proof of any of these. [Apple: notarization](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution).
- CI uses a native Apple Silicon runner, checks all required tests before packaging, and reserves `contents: write` for the tag-only publish job. Third-party action references are pinned to reviewed commit hashes. Publication creates a draft, verifies downloaded asset bytes, then publishes; errors do not silently replace an earlier release. [GitHub: secure workflow use](https://docs.github.com/en/actions/reference/security/secure-use), [GitHub CLI: release creation](https://cli.github.com/manual/gh_release_create).
